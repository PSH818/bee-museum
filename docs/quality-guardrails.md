# 质量守则:视觉资产与基线

> 2026-09-11 立,起因是当日复盘的蜂标本压缩事故:M6 用 meshopt/量化压缩全部 GLB,
> 六种蜂标准标本(顶点色条纹 + 绒毛)被压坏(条纹变暗棕、绒毛不可见),
> 且 25/42 张视觉基线报警后被当作"预期量化漂移"直接重建,坏画面被固化为基线,
> 三天内所有回归"全绿",直至用户对比精模时发现。复盘全文见当日会话,教训摘要在此固化为流程。

## 五条规矩

1. **有损资产处理必须做 A/B 对比。**
   任何压缩、量化、格式转换等有损处理,上线前必须做处理前后**同角度、全身**的渲染对比,
   不能只看一个部位(事故中只验了少毛的腹部特写);顶点色资产(如 bee-hero* 系列)对
   量化最敏感,必须逐个单独验证。"节点结构没变"不等于"外观没变"。

2. **视觉基线重建 = 宣布"现在的样子就是标准",是高危操作。**
   基线报警后想重建,必须先人工确认新画面是**正确**的,而不只是稳定的;
   "复跑通过"只证明新画面可复现,不证明它对。

3. **大规模资产或视觉变更后,给用户人工抽查清单。**
   除了报告测试结果,附上两三个直达链接请用户过目——自动测试的"全绿"替代不了人眼。

4. **重建基线前必看失败证据,汇报必附对比图。**
   Playwright 每张失败基线都生成 expected / actual / diff 三张图。执行
   `--update-snapshots` 之前,必须打开**至少 3 张**失败用例的 actual 逐张查看,
   并在向用户汇报时附上新旧对比截图,然后才允许重建。

5. **失败数超过总数三分之一,一律先按事故调查。**
   "轻微漂移"打不翻大面积基线(事故中 60% 失败仍被归因为量化漂移)。
   超过 1/3 的失败不允许用"预期内"解释,先查根因,查清前禁止重建。

## 已落实的硬防线

- `scripts/compress-models.mjs` 的 `--all` 永久跳过 `bee-hero*`,文件头注明事故;
- 全部模型原件备份于 `models-backup/`(不在 public 内,不随站点部署);
- 花朵 / 巢脾 / 精模(纯材质色、无顶点色)已验证可安全压缩。
